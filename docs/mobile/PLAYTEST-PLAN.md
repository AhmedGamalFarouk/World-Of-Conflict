## Problem Statement

The next real test of World Of Conflict is the 5-10 player playtest (PLAN.md product
gate). Two things stand between today's build and handing an APK to a tester:

1. A legal gate. PLAN.md requires an About screen (name, version + git tag,
   AGPL-3.0 + public source link, "Contains assets from OpenFront (CC BY-SA 4.0)")
   before ANY APK leaves the dev machine, plus a public source repo and a matching
   git tag.
2. Frozen-screen risk. If the map fails to load or the GPU context is lost, the
   tester sees either the upstream desktop error dump (`showErrorModal`, a `<pre>`
   with game/client ids and a copy button) or a blank map under a live HUD. A
   tester who hits that stops, and the playtest log records a crash instead of a
   touch-UX fail point.

## Demand Evidence

None yet. The owner reports OpenFront players asking for a mobile app; that is
interest, not demand. Nobody outside the owner has played an APK. The playtest is
the first demand test, so everything before it should be the minimum that gets a
legal, non-freezing APK into testers' hands.

## Status Quo

Per the owner, OpenFront players do not play on phones today because the web game
is unplayable there. They wait for a PC. This makes the touch controls (tap to
attack, ratio rail, pinch/pan) the core value, with offline play a side benefit.

## Target User & Narrowest Wedge

OpenFront PC regulars who would play on a phone if it worked. They already know the
game, so a playtest with them isolates touch UX from game learning. The wedge is
"OpenFront that feels like a phone game", measured by the existing pass bar:
>=60% finish a game, >=40% start a second.

## Constraints

- Mobile changes stay in the thin mobile layer (HANDOFF.md); never touch
  `packages/engine*`.
- All new text through `translateText()`, keys in the `mobile` block of
  `resources/lang/en.json` only.
- Tests for new logic in `tests/client/MobileShell.test.ts` (jsdom); context-loss
  tests extend the existing `tests/client/MapRendererContextLoss.test.ts`.
- `DESIGN.md` is the visual authority; reuse `wc-*` plates/buttons from
  `mobile-theme.css`.

## Premises (all agreed)

1. The About screen is the only hard code blocker before the playtest; it also
   needs a public repo + matching tag, which is an owner action.
2. Context-loss and map-load-failure screens are cheap insurance: build them now.
3. The top-centre critical event plate is polish: defer until playtesters report
   missing attacks/events.
4. The playtest APK ships as a GitHub Release on the public repo (sideload), no
   Play track yet.

## Approaches Considered

- **A. Thin hooks (chosen).** One new file per screen in `src/client/mobile/`,
  hooked at the two existing choke points. See below.
- B. Routed modals (LazyModals + ModalRouter `#about`, BaseModal): rejected. A
  adds small `isMobileShell()`-guarded branches to four upstream files
  (ClientGameRunner, MapRenderer, GameModeSelector, UserSettingModal); B needs
  those entry-point edits plus routing and modal-registration surface
  (LazyModals, ModalRouter, index.html) for a screen nobody deep-links to.
- C. Static `about.html`: rejected, leaves the app shell, needs its own back
  handling and build-time templating.

## Recommended Approach (A)

**About** — `src/client/mobile/About.ts`, a small Lit overlay using the existing
`wc-*` plate styles, appended to `document.body` on first open.
- Content: "World Of Conflict" wordmark, version line, AGPL-3.0 statement, source
  link, "Contains assets from OpenFront (CC BY-SA 4.0)" with a link to OpenFront's
  source.
- Version: Vite `define` in the mobile build of
  `__WC_VERSION__ = git describe --tags --always --dirty` (falls back to the short
  hash while no tag exists). The source URL is one constant in `About.ts`; until
  the public repo exists it is a placeholder, and the release build refuses it
  (Release order below).
- Entry points: an About button on the offline title screen
  (`GameModeSelector` offline branch) and one in `UserSettingModal` under the
  shell. Android back closes it (`MobileBack.ts`).

**Fatal screen** — `src/client/mobile/FatalScreen.ts` exporting
`showFatal(headingKey, detail?)`: full-screen `wc` plate, one heading, one
"Back to menu" button.
- Back to menu: `window.location.href = homeHref()` (`src/client/Utils.ts:932`,
  returns `"/"` in the shell), the same call the pause overlay's Quit makes in
  `GameRightSidebar.leaveGame()`. The offline app boots `/` straight to the
  offline title screen, and there is no session state to lose offline.
- Idempotent: if a fatal screen is already shown, later calls are ignored (first
  call wins). It sits at the top z-index above HUD, pause overlay and modals.
  Android back while it is shown does the same as Back to menu (`MobileBack.ts`
  checks for it first).
- The original error and stack still go to `console.error`, and the plate shows
  the error message in one small muted line under the heading, so a tester's
  screenshot stays diagnosable.

Which heading, decided by call site (traced in `ClientGameRunner.ts`):
- Start failure. Map files are fetched in `createClientGame`
  (`await terrainLoad` / `loadCachedTerrainMap`) and again in
  `WorkerClient.initialize` (`loadMapFiles`, which rethrows); worker
  `init_error` rejects the same promise. All of these reject `createClientGame`,
  whose `.catch` (ClientGameRunner.ts ~line 298) hides the starting modal and
  calls `showErrorModal(..., "error_modal.connection_error")`. That is the only
  offline caller using that heading, so the shell branch at the top of
  `showErrorModal` maps `heading === "error_modal.connection_error"` →
  `mobile.map_load_failed` ("Couldn't load this map").
- Everything else (worker `errMsg` during play, line ~1021; desync and server
  errors cannot happen offline) → `mobile.game_cant_resume`
  ("Game can't resume").
- `reportGameError` stays called but does nothing offline: the mobile
  `BOOTSTRAP_CONFIG` sets `faroCollectorUrl: undefined` (`vite.config.ts:286`),
  so `initTelemetry` resolves `null` (`Telemetry.ts:84`).
- A test forces `loadMapFiles` to reject and asserts the map-load heading; if the
  trace above is wrong the test fails and we hook where it actually surfaces.

WebGL context loss, in `MapRenderer.ts` under the shell:
- `handleContextLost` already calls `e.preventDefault()` (so
  `webglcontextrestored` can fire) and `handleContextRestored` already wraps the
  rebuild in try/catch. Add: on lost, arm a 3 s restore timer; on restored, clear
  it; in the existing restore catch, call `showFatal("mobile.game_cant_resume")`.
- A `contextLost` flag is set on lost and cleared on restored. The timer only
  counts while `document.visibilityState === "visible"`: if the context is lost
  while hidden, or the page goes hidden while armed, the timer is cleared, and
  on the next `visibilitychange` to visible it is re-armed only if `contextLost`
  is still set (a restore while hidden leaves nothing to re-arm). Android
  routinely drops the context on backgrounding and restores it on resume; that
  must never show the fatal screen.
- Why 3 s: PLAN.md's accepted design block fixes it ("if not restored within 3
  s"). Chromium normally restores within one or two frames once visible.
- Tests: lose → restore within 3 s shows nothing; lose → no restore → fatal after
  3 s; lose while hidden → visible → restore shows nothing; lose while hidden →
  restore while hidden → visible shows nothing; restore throws → fatal.

Strings (en.json `mobile` block, English values):
`about` "About", `about_version` "Version {version}", `about_license` "Free
software under the GNU AGPL-3.0", `about_source` "Source code",
`about_assets` "Contains assets from OpenFront by the OpenFront contributors,
licensed CC BY-SA 4.0, modified for this app", `map_load_failed` "Couldn't load
this map", `game_cant_resume` "Game can't resume", `back_to_menu` "Back to
menu", `about_dev_build` "Development build, do not share". The About screen links the AGPL-3.0 text, the CC BY-SA 4.0 deed and
OpenFront's repo.

Build constant: `__WC_VERSION__` is declared in a `.d.ts` next to the mobile
code and defined in every Vite/Vitest config (mobile build: `git describe`;
web build and tests: `"dev"`), so typecheck and jsdom tests see it.

## Release order (the legal gate)

tree is clean, and `git describe --tags --exact-match` succeeds. Steps, also
written into `docs/mobile/ANDROID.md`:
1. Land About + fatal screens on this branch.
2. Owner creates the public World Of Conflict repo; set the real source URL in
   `About.ts`; commit.
3. Tag that commit (`v0.1.0`), push branch and tag.
4. `npm run android:sync:release`, then assemble the APK right away from that
   clean tagged tree (no commits in between).
5. Attach the APK to the GitHub Release for that tag. Only then share it.

### R3-1 — completeness (minor)

**Problem**

> The legal gate only runs when WC_RELEASE=1 is set; a plain `npm run build-mobile` plus Gradle assemble still produces a shareable APK with the placeholder URL, so the gate is opt-in and step 4 relies on remembering the flag.

**Remedy**

> Either note that non-release builds are distinguishable (dirty/hash version string, placeholder link) and never shared, or have the APK assemble/Release step require the release marker.

### R3-2 — feasibility (minor)

**Problem**

> The success criterion forces a map fetch to 404, but the trace and its test force loadMapFiles to reject. A fetch 404 does not reject by itself; whether it reaches the .catch depends on the loader checking res.ok, which the trace does not confirm.

**Remedy**

> Confirm the map loaders throw on non-OK responses (or add the check), or make the success criterion match the rejection the test forces.

### R3-3 — consistency (minor)

**Problem**

> Choosing the heading by matching the upstream translation key string error_modal.connection_error couples the mobile branch to an upstream key that a merge could rename or reuse for another offline path, silently flipping the heading.

**Remedy**

> Note that the MobileShell test pins this mapping so an upstream rename fails the test, or pass an explicit start-failure flag instead of matching the key.

### R3-4 — clarity (minor)

**Problem**

> Testing dirty-tree and untagged-commit failures needs either a scratch git repo in the test or a pure check function fed git output; the design does not say which, and running the real build in a test would be slow and environment-dependent.

**Remedy**

> Specify that the gate is a small pure function (inputs: source URL, git status, describe result) unit-tested directly, with the build script calling it.
